# Design an Interface

## Expected Outcome

A reasoned visual direction and deliverables that development can apply without reinterpreting decisions: system, tokens, specifications, mockups, states, and behavior across available widths.

## Procedure

1. Read the available product record, content briefs, brand material, existing interface, assets and project rules. Use [references/intake.md](references/intake.md) to ask only for missing inputs that determine the direction.
2. Determine whether the work is a creation, redesign, or refinement. State what must be preserved.
3. Read [references/direction.md](references/direction.md), recommend one primary direction, and connect each choice to the subject. Variants exist only to clarify a real decision.
4. For a new system, establish tokens and the visual guide before pages. Preserve an approved system unless the request explicitly changes it.
5. Read [references/handoff.md](references/handoff.md) and produce only the requested deliverables with real content. Never silently change words to fit the layout.
6. Build [references/accessibility.md](references/accessibility.md) requirements into specifications and states.
7. Render and inspect every visual output at relevant widths and states. Fix what the render reveals and list what remains unverified.
8. Report the selected direction, files, tradeoffs, assumptions, unverified items and recommended reading order.

## Guardrails

- Every shared value becomes a semantic token; a mockup does not redefine a second source of truth.
- Missing factual content remains `[TO PROVIDE: ...]`. Non-factual rhythm copy may be marked `[PROVISIONAL]`.
- Never declare an interface valid without inspecting its render.
- Remove every element without a communicative or functional purpose.
